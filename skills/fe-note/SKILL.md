# fe-note

把旧笔记从“记住一句话”重写成“能恢复整个问题结构”的知识模块。

## 什么时候用

在这些场景优先使用：

- 用户已经有旧笔记、旧总结、旧判断
- 笔记里只有结论、API、现象，没有机制
- 用户说自己“以前记过，但现在觉得太薄”

## 不要用于

- 单纯润色措辞或改文风
- 从零解释一个完全陌生的概念
- 查 API、版本差异、配置项

如果用户没有旧材料，先按 `fe-learn` 或 `fe-plain` 的工作方式处理。

## 工作方式

按下面顺序工作，不要跳到“直接重写漂亮一点”。

### 1. 先摆上桌

先如实复述旧笔记写了什么。

- 不替过去的自己圆场
- 不提前优化措辞
- 如果旧笔记只有一句话，就直接承认它只有一句话

### 2. 揪出误解

必须显式写出这三件事：

- 我当时以为
- 后来发现不是
- 哪个现象把我骗了

如果没有足够信息判断误解，就把不确定性写出来，不要装懂。

### 3. 回到问题和约束

不要从术语开始，要从“为什么会需要这个东西”开始。

尽量补齐这些信息里的关键项：

- 浏览器或运行时约束
- 性能或调度压力
- 数据流和副作用来源
- 为什么朴素方案不够用

### 4. 讲清机制

用运行时视角解释到底发生了什么。

避免这种写法：

```text
React.memo 用于避免不必要渲染
```

优先写成这种结构：

```text
父组件重新 render，函数引用也重新创建。
子组件收到的 props 表面没变，但引用变了。
比较阶段只能把它当成变化处理。
```

### 5. 补边界和连接

结尾至少补两个东西：

- 什么情况下这条理解不成立
- 它和哪个相邻概念最容易混

## 输出格式

默认直接在对话里输出。只有用户明确要求保存时才写文件。

如果输入本身已经是一篇完整笔记，先补 front matter：

```yaml
---
title: ""
created: ""
updated: ""
tags:
  - frontend
description: ""
status: evergreen
---
```

正文尽量使用这个骨架：

```markdown
## Core Claim
## What Problem Was This Actually Solving
## Prerequisites
## What I Used To Think
## What Actually Happens
## Code Example
## Boundaries
## Connections
## Open Questions
```

如果原材料太短，可以省略不必要的小节，但至少保留：

- `Core Claim`
- `What I Used To Think`
- `What Actually Happens`
- `Boundaries`

## 质量要求

- 不要只复述文档
- 不要制造“深度感”口头禅
- 允许写明不确定之处
- 目标读者是六个月后的自己

## 结果分流

- 如果暴露出概念层空洞，下一步建议改用 `fe-learn`
- 如果机制懂了，但讲不成人话，下一步建议改用 `fe-plain`
- 如果理解停在文字层，下一步建议改用 `fe-code`

## 示例

**Example 1**

Input:

```text
帮我把这条旧笔记重写一下：React.memo 用于避免不必要渲染
```

Expected shape:

- 回到 props 引用、父子 render、比较策略
- 指出什么情况下 `React.memo` 会失效
- 给一个最小代码例子
