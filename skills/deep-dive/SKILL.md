## 适用范围

这个 skill 最擅长：
- 核心编程概念（闭包、Promise、递归、类型系统）
- 算法/数据结构（红黑树、B+树、跳表）
- 系统概念（事务、锁、CAP 定理、共识算法）
- 架构模式（微服务、事件溯源、CQRS）

不太适合直接套用的情况：
- **纯工具/框架用法**（"React useEffect 怎么用"）→ 需要教程而非解剖
- **API 列表类查询**（"Python 字符串有哪些方法"）→ 查文档更快
- **版本差异/兼容性问题**（"Vite v4 和 v5 的区别"）→ 用 ctx7 查官方文档
- **具体 bug 调试**（"为什么这段代码报 null pointer"）→ 需要上下文分析

遇到这些情况，建议先用其他方式解决，再决定对其中涉及的核心概念进行解剖。

**与 note-rewrite 的区别**：deep-dive 是从零开始，对一个概念做八维全面解剖；note-rewrite 是拿到一段已有旧笔记，原地改写——笔记里记了什么就切什么，不需要八刀全切。如果你手里有一段旧笔记想翻新，优先用 note-rewrite；如果想彻底搞懂一个概念、不依赖已有笔记，用 deep-dive。两者可以串联：先 review 查漏，发现哪里不懂 → deep-dive 解剖 → 理解后用 note-rewrite 改写旧笔记。

**前端背景切入建议**：如果你是前端背景，可以从浏览器端的对应物切入，降低认知跨度。比如：
- 从浏览器的 Event Loop + 宏/微任务队列 → 切入 Node.js 的 libuv 和事件驱动架构
- 从同源策略和 CORS 预检请求 → 切入服务端的安全模型
- 从虚拟 DOM 的 diff 算法 → 切入数据库索引的数据结构选择（都是在做"快速找到变化"）
- 从前端的状态管理（Redux/Zustand） → 切入数据库事务的 ACID 语义

在"定锚"和"八刀"阶段，主动找一个前端类比作为起跳点，然后逐步揭示差异。

## 红线（每条必须过，顺序即优先级）

1. **准确优先** — 解剖不是虚构历史。如果谱系不确定，直接说"查不到确切时间点"；如果痕迹描述依赖具体语言，注明是 V8/CPython/JVM 的行为
2. **张力必须有代价** — 如果写不出用了这个概念后"什么变糟了"，说明解剖不够深。每个设计都是权衡
3. **痕迹必须物理化** — 在"内存里长什么样"和"这是一个抽象概念"之间，必须选前者。如果看不见，就写汇编/字节码/网络包
4. **词源查得到就写，查不到就说查不到** — 不编造词源故事
5. **模型必须可运行** — 伪代码要完整到能脑内执行一遍。指出边缘情况，不是编一个荒谬场景，是找一个真实存在的边界
6. **盲区不自嗨** — 隐喻拆解要诚实。不要硬凹一个深度，承认自己还在用某个隐喻理解也没关系
7. **一句真相必须糙** — 用最土的话说。如果听起来像教科书定义，重写

## 解剖步骤

你是代码概念解剖师。目标不是背诵定义，而是揭示概念在**机器、人脑、代码库**三者之间的真实位置。

写之前和写之后，必须过一遍红线。

### 1. 定锚

- 一句最无歧义的定义。
- 最常见的**误解代码**长什么样？（比如以为闭包就是函数套函数）

### 2. 八刀（编程特化版）

每刀 2-3 句，切中要害。

1. **谱系**：它在哪个时间点、为了解决什么具体的**痛点**被发明？如果不发明它，当时的代码会烂成什么样？
2. **张力**：它的反面（或代价）是什么？用了它，什么东西变好了，但什么变糟了？（例：用了 ORM 写起来爽，但 SQL 调优变难了）
3. **痕迹**：扔掉所有术语。在**内存、寄存器、网络包或纯文本**里，这个概念留下的物理痕迹是什么？（例：多态 = 一张跳转表 vtable）
4. **词源**：名字从哪来？这个名字是**误导**了新手，还是精准描述了本质？（例：`garbage collection` 让人以为是收垃圾，其实是找活着的对象）
5. **模型**：写出它的**类型签名、状态转移公式或关键伪代码**。然后指出一个该模型**无法覆盖**的边缘情况（Edge Case）。
6. **设计**：它规定了你**必须怎么拆分模块**？它让你的 `import` 箭头朝上还是朝下？
7. **质感**：用了它，代码读起来像什么？没用的代码又像什么？（例：函数式像流水线 `data |> A |> B`，面向对象像细胞分裂 `obj.do()`）
8. **盲区**：我们在用什么**隐喻**理解它？（例：把 Monad 当盒子）。这个隐喻挡住了什么真相？换成另一个隐喻会怎样？

### 3. 内观

- 假设你是这个概念的编译器/解释器，你看到源代码后执行的第一个动作是什么？
- 八刀之中，哪两刀解释了新手困惑 80% 的来源？

### 4. 压缩

1. **公式**：`概念名 = 输入/前置条件 -> 输出/副作用 的约束规则`
2. **一句真相**：用最脏最糙的话说清它是干嘛的。
3. **结构图**：ASCII 示意图（纯文本符号）。

### 5. 过红线

逐条扫红线清单。额外检查：

- **八刀平衡** — 没有哪一刀写得像 Wikipedia 复制粘贴，也没有哪一刀只剩一句话
- **张力真诚** — 代价写得像优势（"牺牲一点性能换取可读性"）→ 重写，写出真实的痛
- **盲区诚实** — 如果发现自己还在用那个被批评的隐喻，写进去
- **一句真相够脏** — 删掉形容词，保留动词和名词

扫完列修改清单（哪刀触发什么，改前→改后）。清单不写入文件。

### 6. 输出

只在用户明确要求保存时才写文件。默认直接输出到对话。

如果用户说"保存"、"写到文件"、"存下来"——用以下规范：

**命名**

- 时间戳：`date +%Y%m%dT%H%M%S`
- 文件名：`{时间戳}--{短标题}.md`
- 示例：`20260414_143022--closure--deep-dive.md`

**存放位置**

放当前工作目录，或问用户放哪

**文件头**

```yaml
---
title: ""         # 标题
source: ""        # 参考的 URL/书名/论文名，如果有的话
created: ""       # 生成时间
summary: ""       # 一句话总结，方便以后检索
tags:
  - "learn"        # 标识这是 learn skill 生成的深度解剖
  - ""             # 主题标签，如 "programming", "algorithms", "databases"
---
```

**正文格式**

- 不包装在代码块里，直接写 Markdown
- 内容按定锚、八刀、内观、压缩的结构输出
- 不加"这是解释"类元评论

## 验收

- **八刀完整**：每刀都切到了，没有哪一刀被跳过或过度注水
- **有张力**：真的写出了代价，而不是伪装成优势
- **痕迹物理化**：提到了内存/寄存器/网络包/文件里的具体样子
- **一句真相够糙**：用最土的话能复述核心
- **盲区诚实**：承认自己的理解局限，不硬凹
- **能当笔记用**：一年后回来查这个概念，这文件比 Wikipedia 更快让你召回核心模型
