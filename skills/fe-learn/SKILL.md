# fe-learn

把一个前端概念从“会用”切到“知道它为什么这样存在”。

## 什么时候用

在这些场景优先使用：

- 用户会用，但没搞懂本质
- 用户想知道“为什么这样设计”
- 用户想把一个概念接到浏览器、框架和工程实践上

## 不要用于

- API 用法题
- 版本迁移和配置题
- 需要先复现现场的 bug 调试

如果用户只是想听人话版，先按 `fe-plain` 的工作方式解释。

## 工作方式

按下面顺序展开，避免直接堆知识点。

### 1. Anchor

先用一句不花哨的话说清：

- 它是什么
- 它解决什么痛点

### 2. 从七个角度切

尽量都切到；如果某一角信息不足，就明确写“这里暂时无法确定”。

1. `History`
   它在什么背景下被逼出来？如果没有它，旧方案烂在哪里？
2. `Engine Or Browser Reality`
   浏览器、JS 引擎、调度器里真实发生了什么？
3. `Framework Differences`
   React、Vue、原生浏览器或其他框架如何看待它？差异在哪里？
4. `Formal Shape`
   用关键数据结构、状态转移或伪代码描述它。
5. `Pattern Mapping`
   它更接近什么设计模式、架构模式或系统问题？
6. `Common Traps`
   最常见误解从哪里来？
7. `One Insight`
   一句能把它钉住的话。

### 3. 写清代价

每次都要写：

- 它解决了什么
- 它让什么变好了
- 它又把什么变糟了

如果写不出代价，说明分析还停在表面。

### 4. 压成最小模型

最后把内容压成：

- 最小心智模型
- 一个和前端日常代码有关的例子
- 用户下一步该做什么

## 输出格式

默认直接在对话里输出，用这个骨架：

```markdown
## Anchor
## 1. History
## 2. Engine Or Browser Reality
## 3. Framework Differences
## 4. Formal Shape
## 5. Pattern Mapping
## 6. Common Traps
## 7. One Insight
## Tradeoffs
## Minimal Mental Model
## Suggested Next Step
```

如果某一节没有足够依据，直接写“不确定”或“暂缺可靠信息”，不要硬编。

## 质量要求

- 重点是机制和取舍，不是百科抄写
- 能落到浏览器、引擎或框架里的真实行为
- 有代价，不只写好处
- 最后一段必须能帮助用户长期记忆

## 结果分流

- 如果用户懂了但还讲不清，下一步建议改用 `fe-plain`
- 如果用户想把理解写回旧笔记，下一步建议改用 `fe-note`
- 如果用户想验证猜想，下一步建议改用 `fe-code`

## 示例

**Example 1**

Input:

```text
彻底搞懂 React Fiber
```

Expected shape:

- 说明旧调和流程为什么不够
- 讲清时间切片、可中断、优先级
- 给一句能长期记住的顿悟
