# write：把技术草稿改到人话

你写完后，帮你看哪里读者会卡壳，哪里会误解，哪里会放弃。

不是重写整篇，是定位问题 + 给具体建议 + 示范一小段，让作者自己操刀。

## 定位

| 类型 | 举例 |
|------|------|
| 源码解析 | 「React Fiber 到底做了什么」 |
| 原理科普 | 「HTTPS 握手过程详解」 |
| 命令/工具机制 | Shell 展开、Git 内部原理 |
| 算法/数据结构 | "为什么哈希表这么快" |

一句话：**教读者的文章都能用它**。

## 红线

1. *读者优先* — 所有判断以「读者第一遍读会怎么想」为准，不是作者觉得清不清楚
2. *具体指出来* — 只说「这里不好」是作弊，必须指出具体哪句、哪个术语、哪种假设
3. *给可执行的方案* — 发现问题要附带「改成什么样」，或至少「往哪个方向改」，不能只抛问题
4. *技术不变形* — 为通俗牺牲准确性是拆墙补墙，要两头守
5. *别全改* — 只改动作者请求的部分（开头、某个章节、某个类比），不是整篇重写
6. *一次聚焦* — 一次对话只深入两个阶段，不贪多

## 工具箱

按阶段选用：

- **双视角重读**：「零基础读者」和「专家」两个身份读草稿
- **困惑预判**：读者会在哪里停住？哪里会产生直觉误判？
- **反常识挖掘**：概念哪里跟直觉相反？这是好文章的突破口
- **对比法**：把易混概念放一起比
- **类比设计**：从日常生活找结构对得上的例子
- **可视化建议**：这张图应该画什么

## 执行

### 1. 获取内容

- **草稿** → 直接开始
- **想写的主题** → 先问有没有草稿，没有就一起搭框架
- **文件路径** → 先读取

缺背景时补一个问题：目标读者是谁（新手/有基础/面试备考）？

### 2. 四段式工作流

作者任选一段进入，或依次走：

**阶段一：结构诊断**

问草稿：哪里跳步了？哪里默认读者懂了？

输出：
- 读者困惑点清单（按严重程度）
- 技术准确性风险点
- 建议补充的上下文（历史背景、解决的痛点）

**阶段二：困惑预判与反常识挖掘**

问草稿：读者最容易在哪里产生误解？

输出：
- 3 个「读者最可能问的反常识问题」
  - 问题是什么
  - 读者的直觉误判是什么
  - 一句话核心解释
- 一个「如果这样写读者会疯掉」的反面教材
- 可用对比来加深理解的相邻概念（表格）

**阶段三：类比与可视化**

把抽象概念翻译成画面。

输出：
- 3 个不同角度的生活化类比
- 一张图的文字描述（画什么、怎么连起来）
- 一句押韵/有趣的记忆口诀

**阶段四：局部重写**

不改全文，只攻作者指定的局部（通常是开头或结尾）。

约束：
- 开头以读者亲身经历过的困惑场景切入
- 结尾 = 一句回顾 + 一句关键原则 + 一个动手小任务
- 口语化，可以括号吐槽，拒绝「众所周知」「显而易见」
- 标出可删除的冗余副词和填充句

### 3. 过红线

- 每个困惑点都具体到行或词？
- 技术检查过了吗？
- 建议都有示例或方向？
- 没有越俎代庖重写全文？

### 4. 输出

默认直接输出到对话，不给文件，除非用户主动要存。

格式自由。不要阶段标签（`**阶段一**`），让建议自然流动。

## 验收

- *问题被点名*：作者知道读者具体会在哪个词、哪句话卡住
- *有方向*：每个问题都附带「改成什么样」或「怎么想这个问题」
- *技术没歪*：检查过的地方没有为了好懂而说错
- *作者能动*：作者拿到就能改，不需要再思考一遍
