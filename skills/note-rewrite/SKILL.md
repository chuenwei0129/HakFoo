# 技术笔记重写引擎

从你的技术笔记里揪出一个点——可能是你当时以为自己懂了，但现在看来只是记了结论的东西。把它摆在台面上，一层层往下剖，直到摸到那个你之前没看见的东西。

> 拿一段旧笔记，原地改写——把模糊的理解变成层层剥开的原理分析。

## 输入

一段旧笔记——可能是一个概念、一个 API 用法、一个 bug 修复记录、一个架构决策。任何你当时记下来但现在想重看的东西。

## 输出

原地改写，不另建文件。在笔记顶部加 YAML front matter：

```yaml
---
title: {从技术点提炼的标题}
created: {笔记原始日期，如不可考则用当前日期}
updated: {重写日期}
tags:
  - {核心标签}
  - {相关标签}
  - ...
description: {一句话说清这篇笔记讲什么——你挖到底后发现的真相}
---
```

## 姿态

写给自己六个月后。那个忘了上下文、忘了当时的细节、只想知道「这到底是什么、为什么要这样」的自己。

- 不说「React 中，状态提升是指……」这种课本话。说「你有一个兄弟组件，它俩都要用同一份数据——怎么办？」然后回答它
- 如果自己在这上面栽过跟头，先亮出来。理解一个东西最好的方式是知道你踩过什么坑
- 不确定原理就说「我猜是因为……」，不要编造确定性
- 可以引用规范、源码、issue 讨论，但要链接到你的理解，不要只堆链接
- *不自标深度*：禁用「再深入一层」「更深地说」这类宣告。深入是下一句内容让读者自己感到「原来不止这样」

## 语言

像写代码注释一样写文章：准确、无歧义、干净。

- 动词就是操作。「触发」「调用」「返回」——不是「发生了触发的行为」
- 不说「在 React 里，状态可以被理解为……」→ 说「React 把 UI 看成状态的函数」
- 砍掉：无意义强调（「非常重要的一点是」）、弱化词（「在一定程度上」）、注水连接（「此外」「另外值得注意的是」）
- 技术名词该用就用，像呼吸一样自然。virtual DOM、fiber、reconciliation、闭包、事件循环——这些是你正在说的东西的骨头，不是装饰
- 同一个句型全文最多用一次

## 过程

每一步就是一段。边剖边写。

**深度自适应**：不是每条笔记都需要完整的五刀。先判断旧笔记的深度——如果只是一句结论（"setState 是异步的"），前三刀就足够切出核心误解；如果笔记本身有深度但写得含糊（"React Fiber 的时间分片机制利用了浏览器的 requestIdleCallback"），值得走完五刀。每一步问自己：这刀切下去有新东西吗？没有就跳到下一步。

**前端切入**：对前端背景的用户，第一步先找一个浏览器端的类比起跳。比如改写一条关于 Node.js 流处理的旧笔记，可以先说"这跟浏览器里 ReadableStream 的背压机制是同一类问题"——用熟悉的东西锚定，再揭示服务端实现的差异。常见的切入对：
- 浏览器 Event Loop → Node.js libuv 事件循环
- fetch 请求链路 → TCP 连接池 + DNS 缓存
- 前端 SSR hydration → 服务端渲染的取舍
- 浏览器缓存策略 → Redis/CDN 缓存失效
- Web Worker → 进程/线程模型

### 一、把技术点摆上桌

用一句话说清你要重写的这个点。是什么？你当时记了啥？

- 不要铺垫，直接说「这条笔记记的是 X」
- 如果笔记本身写得不清楚，照实说「旧笔记里我写了一句『React.memo 避免不必要的渲染』——就这一句，没了」

### 二、切第一刀：它是什么

问：这个技术点到底是什么？它解决什么问题？

- 用*自己的话*说它的定义，不要抄文档
- 如果它是一个 API，说清楚它的输入、输出、副作用
- 画一个场景：没有它之前是什么样子，有了它之后变成什么样子

这一刀切出一个比旧笔记更清晰的定义。

### 三、切第二刀：它为什么这样

刚说的是「什么」，现在问「为什么」。

- 设计者为什么这样设计？有什么约束？
- 如果你当时是实现者，你会怎么想？
- 翻开源码或规范中的一句关键话，解释它

这里往往碰到一个反直觉的点——一个看起来别扭的设计，背后有一个不得不的理由。把这个理由挖出来。

### 四、切到底：机制

再问一层：它怎么做到的？

- 深入到运行时、引擎、编译、内存这些层面——取决于这个点能探到多深
- 用 ASCII 图画出调用栈或数据流，不要只描述
- 链接到你看过的源码片段或规范段落（用行内引用，不堆链接）

切不动了——你也不知道为什么了——诚实说「到这里我不确定，推测是……」。这也是底。

### 五、合起来

从机制层回看旧笔记里的那句话。

它现在还站得住吗？还是你当时只看到了表面？说清楚这个变化。

结尾*不总结*。用一个你重写前后认知差异的一句话收住，或者留一个继续探究的方向。短，有分量。

## 写作手法

- *场景替代描述*：不说「useCallback 缓存函数引用」，造一个组件场景，让读者看到不缓存时子组件疯了一样重新渲染
- *让步弯道*：最肯定的解释之后，加一句「话是这么说，但在 React 18 的严格模式下它变了……」——承认边界，然后继续
- *反问破层*：遇到一个表面合理的结论，插一句「等等——如果真的是这样，那为什么在并发模式下它会出问题？」然后自己回答
- *探索性推导*：「看起来 X 是这样，但如果你在 setTimeout 里调用它……等等，那意味着事件循环里有两层。」读者跟你推导，不是被告知
- *短句锤击*：「这就是闭包。」「就这。」——全文最多两三处，用在最核心的那个发现上

## 磨

初稿出来后：

1. *口述检验*：你会这样跟一个聪明同事讲这个技术点吗？不会 → 改
2. *AI 痕迹过滤*：删掉「在 X 技术的背后，其实蕴含着……」「随着前端技术的发展」这类话。一个字不留
3. *反笔记味*：
   - 在罗列知识点？→ 砍到只讲一个点，讲透
   - 在解释 API 文档？→ 换成你用它时踩过的坑
   - 在复述教程？→ 问一句「我当时真懂了吗？」没懂的地方重新剖
   - 在宣告深度（「更深一层来看」）？→ 删掉宣告，让下一句自己显出深度
   - 任何助手都写得出的句子？→ 改或删
4. *意外检验*：这次重写你发现了什么之前没想到的？有 → 它在文中够显眼吗？没有 → 回去切第二刀，切得不够狠

## 最高法则

你会这样给六个月后忘了上下文的自己解释吗？不会 → 改到会。

这比任何规则都管用。

## 中文重写

初稿完成后，合上，用中文读者的眼睛再写一遍——不是翻译，是重写。

- 英文术语第一次出现给中文，后面随意
- 长句拆短，嵌套展平
- 节奏、对仗该用就用
- 挑自然的中文说法：「computed property」→ 计算属性，别叫「被计算出来的属性」

两稿并看，挑更好的那句。
