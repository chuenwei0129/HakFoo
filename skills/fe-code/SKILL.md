# fe-code

把“我听说如此”变成“我亲眼看见它这样跑”。

## 什么时候用

在这些场景优先使用：

- 用户想验证一个前端机制
- 用户想把概念变成最小练习
- 用户已经有结论，但从没做过实验

## 不要用于

- 生产级功能开发
- 大型脚手架搭建
- 与概念无关的随意 demo

如果用户还没形成清晰猜想，先按 `fe-learn` 的工作方式补概念层。

## 工作方式

### 1. 先定义猜想

把要验证的话写成一句清楚的话，避免实验目标漂移。

### 2. 只做最小环境

尽量缩小环境：

- 能用一段 HTML + JS 验证，就不要上框架
- 能用一个组件验证，就不要起完整应用
- 能观察一件事，就不要同时观察三件事

### 3. 指定观察点

明确告诉用户要看什么，例如：

- 执行顺序
- 渲染次数
- 引用变化
- layout / paint / effect 时机

### 4. 预告预期结果

在运行前先写出你预期会看到什么，这样实验失败时才有信息量。

### 5. 写结论回流

实验结束后，必须回写：

- 猜想被证实还是被推翻
- 这修改了哪条旧理解

## 输出格式

默认直接在对话里输出，用这个骨架：

```markdown
## Hypothesis
## Goal
## Smallest Setup
## Minimal Code
## What To Observe
## Expected Result
## Failure Modes
## What This Changes In My Model
```

如果适合，再补：

```markdown
## Optional Test Harness
```

## 质量要求

- 环境越小越好
- 观察点必须具体
- 要能区分“证实了什么”和“推翻了什么”
- 不要为了炫技把实验做复杂

## 结果分流

- 如果实验产出了新理解，想沉淀成笔记，下一步建议改用 `fe-note`
- 如果实验结果和预期不一致，回去补概念层，下一步建议改用 `fe-learn`

## 示例

**Example 1**

Input:

```text
给这个知识点配一个最小代码实验：事件循环里的微任务和宏任务
```

Expected shape:

- 明确要观察的执行顺序
- 给最小代码
- 说明这个实验会推翻哪些常见误解
