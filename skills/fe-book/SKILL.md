# fe-book

读技术书时，先抓作者在解决什么问题，再决定细节值不值得记。

## 什么时候用

在这些场景优先使用：

- 用户准备读一本技术书，不想被细节淹没
- 用户已经读过，但说不出作者到底想解决什么
- 用户怀疑自己记了一堆 API，却没抓住骨架

## 不要用于

- 一篇短博客
- 一个 API 怎么用
- 一本非技术类书籍的读后感

如果输入主要是文章、源码或 RFC，改按 `fe-read` 的工作方式处理。

## 工作方式

### 1. 先找核心问题

不要先列知识点。先找这本书到底想补什么认知缺口。

### 2. 挖默认假设

说明作者默认读者：

- 已经知道什么
- 愿意接受什么
- 忽略了什么

### 3. 提炼分析框架

找出作者反复使用的观察角度，例如：

- 运行时
- 抽象层次
- 调度与副作用
- 兼容性与工程约束

### 4. 区分长期资产和时代噪音

必须把这些分开：

- 时代特定的 API、工具背景、版本限制
- 可以迁移到今天的长期思路

### 5. 给最小实践路径

告诉用户下一步最值得做什么：

- 先做哪个最小实验
- 再写哪一类笔记
- 哪个章节值得精读，哪个可以略读

## 输出格式

默认直接在对话里输出，用这个骨架：

```markdown
## Core Problem
## Default Assumptions
## Analysis Framework
## Core Claims
## God View Summary
## What Is Timeless vs Dated
## Minimal Practice Path
```

如果用户只给了一章或一段摘录，就按同样骨架缩小到局部，不要假装评估了整本书。

## 质量要求

- 不把拆书写成目录摘要
- 要区分“作者写了什么”和“作者真正反复在乎什么”
- 必须分开长期有效和时代特定内容
- 结尾要给一个可执行的下一步

## 结果分流

- 如果用户想把其中一个观点写回个人知识库，下一步建议改用 `fe-note`
- 如果用户想把书里的主张做成实验，下一步建议改用 `fe-code`

## 示例

**Example 1**

Input:

```text
帮我拆《JavaScript 高级程序设计》
```

Expected shape:

- 说清这本书试图建立什么 JS 运行时骨架
- 区分哪些部分偏 API 手册，哪些部分是长期资产
- 给一个阅读顺序或实践顺序
