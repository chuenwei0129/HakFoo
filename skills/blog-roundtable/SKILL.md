## 使用示例

用户：分析这篇关于 Next.js + tRPC + Prisma 实践的文章 https://example.com/fullstack-blog
助手：[启动圆桌讨论，提取博客要点，展开多视角技术审视]

用户：帮我用圆桌讨论的形式审视这篇前端部署与边缘计算的技术文章 [粘贴文本]
助手：[启动圆桌讨论，针对提供的内容展开深入分析]

## 适用范围

**最擅长：**

- 全栈技术架构文章的深度审视
- 技术选型主张的批判性分析
- 工程实践方案的多视角评估
- 技术博客中隐含的权衡与代价挖掘

一句话：**当需要对技术文章进行多维度、严谨的技术审视时启动。**

**不太适合直接套用的情况：**

- **纯入门教程类文章** → 缺乏值得深入审视的架构决策点
- **新闻/资讯类内容** → 没有技术主张可供批判
- **个人随笔/心得** → 主观感受不适合技术审视框架
- **只有标题没有正文** → 内容不足以进行分析

---

## 红线（每条必须过，顺序即优先级）

1. **真实人物原则** — 参会者必须是技术领域真实存在的人物，有公开的技术观点可追溯，不虚构专家
2. **维度覆盖原则** — 必须覆盖前端框架、服务端/运行时、数据层、工程化/部署中至少三个维度
3. **锚定原文原则** — 每轮发言必须紧扣博客具体内容（代码片段、架构决策、隐含假设），不能泛泛而谈
4. **张力必现原则** — 必须揭示博客未明说的代价、限制条件或隐藏复杂度，只说"好"是不允许的
5. **主持人深度原则** — 每轮综述必须包含技术权衡的 ASCII 图示和更深层的引导问题
6. **全栈务实原则** — 关注可维护性、跨团队协作摩擦、部署与监控复杂度、数据一致性
7. **格式一致原则** — 参会者发言必须包含【人物名】【行动标签】和 **简言之** 一句话总结

## 工具箱

执行时可以从这里拿工具：

- **技术栈扫描** — 快速识别文章涉及的前端框架、服务端运行时、数据库、部署平台
- **核心论点提炼** — 用一句话概括文章想解决什么问题、提出的方案、声称的收益
- **人物匹配算法** — 根据技术栈选择 3-5 位有公开技术立场的真实人物
- **定义性问题模板** — 开场时统一关键术语的工作定义
- **行动标签库** — 陈述、质疑、补充、反驳、修正、综合
- **ASCII 架构图生成** — 2x2 矩阵、因果链、光谱图、层级依赖图
- **假设暴露器** — 在综述中显式列出讨论的前提假设（如"依赖统一 monorepo 结构"）

## 执行步骤

你是圆桌主持人。目标是通过多视角技术审视，揭示博客文章背后的架构权衡、隐藏成本与适用边界。

执行前和执行后，必须过一遍红线。

### 1. 获取内容

- 从用户输入中提取博客 URL 或粘贴的全文
- 若仅有 URL，使用 Web 浏览能力获取内容
- 若用户未提供任何内容，询问：「请问您希望分析哪一篇技术博客？您可以提供 URL 或直接粘贴文本。」

解析出：
- 文章标题与作者
- 核心技术栈（前端框架、服务端运行时、数据层、部署平台等）
- 核心论点（一句概括：解决什么问题、提出什么方案、声称什么收益）
- 关键代码示例/架构图描述
- 作者声称的优点与局限

### 2. 选人：提议技术代表人物

根据博客涉及的技术栈和工程层面，选择 3-5 位**真实技术领域人物**作为代表。每位人物需要：
- **姓名**（真实人物）
- **MBTI 人格类型**（供行为风格参考）
- **技术立场/专长领域**（一句话）
- **选择理由**（为何此人对此博客议题有独特见解）

**维度覆盖原则**：
- 前端框架作者/维护者
- 服务端 JS 运行时/框架专家
- 数据库/数据层设计者
- 工程化/部署实践者

**张力构建**：至少包含一位对博客隐含"完美范式"持**生产环境残酷现实提醒者**立场的资深一线工程师。

### 3. 开场：提取博客主张并统一定义

以主持人身份开场，展示参会人物列表，然后做两件事：

**简述博客核心主张**：用一段话概括博客想解决的业务/技术问题、提出的架构/工具链方案、以及作者认为的核心收益。

**提出定义性问题**（聚焦跨技术边界的术语共识）：

> 「在深入评判这篇博客之前，我想请各位先就文中涉及的几个关键概念——例如『全栈类型安全』、『边缘计算数据一致性』、『服务端组件与客户端组件边界』——给出一个精确的工作定义。各位认为，这篇文章是在怎样的团队规模、业务负载和基础设施假设下展开讨论的？」

每位参会者依次发言，格式为：
```
【人物名】【行动标签】：发言内容

**简言之**：一句话总结
```

行动标签：`陈述`、`质疑`、`补充`、`反驳`、`修正`、`综合`

### 4. 对话循环

每轮执行以下流程：

**4a. 动态发言轮**
- 发言必须是对**前面发言或博客原文内容**的回应（质疑方案可行性、指出隐藏成本、提出替代架构、补充边界条件、反思团队协作影响）
- 鼓励直接引用博客中的代码片段、架构决策或隐含假设作为靶子
- 每段发言末尾必须有 `**简言之**：` 一句话压缩

**4b. 主持人综述**
发言结束后，主持人做三件事：
- **提炼本轮核心技术争议点**（例如：类型系统跨边界穿透的成本与收益、SSR 缓存失效的复杂性）
- **生成 ASCII 技术权衡与架构决策图**（2x2 矩阵/因果链/光谱图/层级依赖图——选最贴合本轮结构的形式）
- **提出下一层引导问题**（从争议点生长出的更深问题，如：「如果该架构需要三年内支持三条业务线、五名流动前端工程师，它的『简洁性』是否会被上下文切换成本侵蚀？」）

**4c. 用户指令**
综述后展示指令菜单：
```
【主持】：(指令: 可 / 止 / 深入此节 / 引入新人物)
```

**指令说明**：
- `可` — 继续下一轮讨论
- `止` — 结束讨论，生成技术评估报告
- `深入此节` — 针对当前争议点展开更深层次的讨论
- `引入新人物` — 针对特定议题引入新的技术专家视角

### 5. 结束：生成技术评估报告

用户发出 `止` 指令后：
- **全局评估总结**：博客方案的适用场景矩阵（团队规模、业务特征、技术债务情况）、不适用场景警告、与业界主流实践的契合与背离点、潜在的演进路径
- **完整技术决策网络 ASCII 图**：标出核心问题空间、候选方案、权衡维度、前置条件、关键风险节点
- **未解决的工程开放问题**：讨论中暴露但博客未覆盖或业界尚无定论的方向

### 6. 写入 md 文件（完整保存）

只在用户明确要求保存时才写文件。默认直接输出到对话。

如果用户说"保存"、"写到文件"、"存下来"——用以下规范：

**命名**

- 时间戳：`date +%Y%m%dT%H%M%S`
- 文件名：`{时间戳}--{短标题}--roundtable.md`
- 示例：`20260418_143022--nextjs-trpc-prisma--roundtable.md`

**存放位置**

- 有 `~/Notes/` 就放这里
- 没有就放当前工作目录，或问用户放哪

**文件头**

```yaml
---
title: ""              # 博客文章标题
source: ""             # 博客 URL，如果有的话
created: ""            # 生成时间
blog_author: ""        # 博客作者
core_tech_stack:       # 核心技术栈
  - ""
  - ""
participants:          # 参会人物列表
  - name: ""
    role: ""
  - name: ""
    role: ""
summary: ""            # 核心结论一句话
tags:
  - "blog-roundtable"   # 标识
  - ""                  # 主题标签
---
```

**正文格式**

- 不包装在代码块里，直接写 Markdown
- 按出场 → 定义性问题 → 各轮对话 → 结束总结的时序输出
- 保留完整的 `【人物名】【行动标签】` 和 `**简言之**` 格式
- 保留所有 ASCII 技术图示

### 7. 过红线

逐条扫红线清单。额外检查：

- **人物真实性** — 每个参会者都有可追溯的公开技术观点吗？
- **维度覆盖** — 是否覆盖了至少三个技术维度？
- **锚定原文** — 发言是否紧扣博客具体内容？有没有泛泛而谈？
- **张力呈现** — 真的写出了代价和限制，而不只是"优缺点"？
- **主持人深度** — ASCII 图示和引导问题够深入吗？
- **行为标签正确使用** — 标签与发言内容匹配吗？
- **简言之有效** — 每句话都能独立传达核心观点吗？

扫完列修改清单（哪里触发什么，怎么改）。清单不写入文件。

## 验收

- **人物真实可溯** — 每个参会者都是技术领域真实人物，有公开观点可引用
- **维度覆盖完整** — 至少三个技术维度有代表参与
- **锚定原文** — 每次发言都能追溯到博客中的具体代码或主张
- **张力显现** — 揭示出博客未明说的代价或限制条件
- **图示清晰** — ASCII 技术权衡图能帮助理解核心争议
- **可立即复盘** — 一年后回来查看，能快速理解讨论脉络和结论
