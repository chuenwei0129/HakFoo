# fe-read

读材料时先给地图，再陪用户进重点区域。

## 什么时候用

在这些场景优先使用：

- 用户要读博客、源码、RFC、设计文档
- 用户不知道先看哪里
- 用户想从材料里提取“为什么这么设计”

## 不要用于

- 完整代码审查
- 线上 bug 排查
- 纯新闻摘要

如果用户要读的是完整技术书，改按 `fe-book` 的工作方式处理。

## 工作方式

### 1. 先画结构图

先告诉用户这份材料分几层：

- 先看哪里
- 哪些地方是主干
- 哪些地方可以暂时跳过

### 2. 标热点

指出真正关键的段落、函数、图示或论点。

至少标出：

- 哪一段最值得细读
- 哪个地方最容易误读
- 哪个问题最值得带着看下去

### 3. 追设计动机

对关键位置持续追问：

- 为什么作者要这么写
- 替代方案是什么
- 代价是什么

### 4. 接到已知模型上

尽量把新材料挂到用户熟悉的前端概念上，降低阅读跳跃感。

### 5. 给继续阅读的方向

告诉用户：

- 接下来应该精读哪一部分
- 哪一部分可以后看
- 如果读完仍卡住，下一步更适合换哪个 skill

## 输出格式

默认直接在对话里输出，用这个骨架：

```markdown
## Structure Map
## What To Read First
## Hotspots
## Why It Is Written This Way
## Cross Links
## Questions To Carry While Reading
## Suggested Next Step
```

如果是英文或极高密度材料，可额外补：

```markdown
## Three-Layer Translation
```

三层分别是：

- 原句在说什么
- 作者真正想表达什么
- 这和用户已有知识怎么接上

## 质量要求

- 不要把伴读写成摘要
- 不要平均用力地讲每一段
- 真正关键的是入口、热点和设计动机
- 如果信息不足，明确说“这里只能推测”

## 结果分流

- 如果读完发现概念没懂透，下一步建议改用 `fe-learn`
- 如果读完想写回知识库，下一步建议改用 `fe-note`
- 如果读完想做最小实验验证，下一步建议改用 `fe-code`

## 示例

**Example 1**

Input:

```text
带我读这段 React 源码
```

Expected shape:

- 给出入口和调用链
- 标出真正关键的函数
- 解释为什么这里要这样拆模块
